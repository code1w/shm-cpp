# 等待协议闭合与进展检查

本轮构建显式状态图，补充有限轮次模型之外的协议闭合检查，并验证“单次处理期间游标不绕满整圈”这一前提是否必要。生产代码未修改。

## 模型与结果

`test/modelcheck/wait_protocol_graph.py` 逐状态执行双方协议动作，不设消息总数或执行轮数上限，直到所有可达状态闭合。每次通知拆成标志检查、exchange 清零和 eventfd 写入，保留通知在途状态；读方拆成通知排空、读取前取基线、Peek、完整帧消费、置 Waiting、栅栏、复查、撤销或 poll。

状态记录占用、缩小的循环游标、等待标志、通知是否可读、双方程序位置和本轮游标进展。消费只移除完整帧，半帧可以合法等待。通知抽象为可读位，多次通知合并，与本模型所需的可唤醒性质对应；不验证真实 eventfd 计数、syscall 错误或资源生命周期。

| 容量 / 游标模数 / 帧长 | 闭合状态数 | 完整帧待处理状态数 | 不消费的循环 / 真正终止状态 |
|---|---:|---:|---:|
| 2 / 8 / 1 | 13,651 | 9,387 | 0 / 0 |
| 2 / 8 / 2 | 7,291 | 2,616 | 0 / 0 |
| 4 / 8 / 2 | 11,837 | 6,970 | 0 / 0 |

上述模型限制单次基线捕获至复查间的新发布进展小于游标模数，并要求写方履行通知义务。闭合图中没有“完整帧待处理、读方睡眠、通知不可读、写方已完成通知阶段”的坏状态。

这是 SC 动作交错模型，栅栏在模型中是一个程序步骤，不引入弱内存 reads-from 选择。因此不能用它判断删除栅栏是否安全；此前 GenMC/RC11 与 Z3 对此已有反例。小容量和小模数也不是对全部实际容量的参数化证明。

## 通知在途必须作为义务保留

写方 exchange 已将 Waiting 清零，但 eventfd 尚未写入时，读方可能睡眠且环中已有完整数据。这是合法的暂态，不应立即判丢唤醒。

模型仅在写方回到“通知义务已完成”的空闲阶段时判坏状态。故意把最后的通知写入丢弃后，314 个已访问状态内找到反例。该对照说明，模型没有把“抢到了 Waiting”错误地当成“已经完成唤醒”。

前提是通知步骤最终执行。若进程崩溃或执行线程永久停止，协议本身不能保证 eventfd 唤醒；本项目另用 UDS EOF 处理退出场景。

## 进展性质检查

在闭合图中，只保留“已有完整帧”的状态，并删除消费完整帧的边。生产发布不会减少占用，因此只要还没有消费，完整帧待处理这一性质持续成立。

对这个子图执行拓扑消除，三个配置都无剩余循环；同时没有真实的无可执行动作终止状态。因而，在该有限抽象中，已有完整帧不可能经历无限多个有效协议步骤却始终不被消费。

这依赖程序持续执行可用步骤，或相应的公平调度前提；不能证明暂停线程、挂起进程或无限外部 stutter 时的进展。它也不是 RC11 弱内存无限执行的 liveness 证明。计数器有限且状态空间闭合，使论证覆盖这些抽象配置的任意多次状态循环，而不是仅跑指定轮数。

## 新反例：旧基线绕满整圈的 ABA

取消“本轮进展小于模数”约束后，模 8、容量 2、帧长 2 的模型在 5,858 个已访问状态内找到 50 步反例。核心步骤：

1. 读方捕获 seen=2，并进入持续排空。
2. 写方在读方处理期间反复发布，读方消费完整帧；等待标志为 Awake，写方合法省略通知。
3. 游标经历 2→3→4→5→6→7→0→1→2，恰好回到旧基线。
4. 读方在只看到一个字节的半帧时结束排空；第二字节随后发布，成为完整帧。此时标志仍为 Awake，写方不通知。
5. 读方置 Waiting 并复查，write_pos 数值等于旧 seen，于是睡眠；环中有完整帧，eventfd 不可读，写方已经完成。

反例不需要削弱栅栏，问题是基线的数值身份被复用。它解释了上一轮为什么不能删除“单次处理进展不绕满整圈”的论证前提。

实际源码在 `ShmConnection::DrainRing()` 调用 DrainRingOnce 前取 WritePos，再用同一个 seen 调用 PrepareWait。真实游标是 uint64_t，对应 ABA 条件是同一次处理期间新发布累计绕过完整的 2^64 字节，而非跨越 UINT64_MAX 一次。在 10 GB/s 下该数据量约需 58.5 年，且必须持续使用同一个处理基线；这与受控本机消息量场景相距极远。

因此，本轮发现的是等待协议无条件完备性的一项理论限制，不是实际 64 位实现的故障复现。模型没有覆盖真实 codec、帧计数、地址映射及其其他约束，不能把缩小模型的反例直接称为生产事故。已有的普通数值回绕测试依然有效：一次越过 UINT64_MAX 并不等于推进满 2^64 字节后再次使用相同基线。

若未来要求彻底移除这项前提，可以研究在最后一次无法继续消费时捕获相应发布快照；停止释放空间后，写方进展受容量限制。半帧场景不能简单改为 ReadPos 基线，否则可能反复尝试不完整帧。这只是待验证的设计方向，本轮没有改动生产读取路径。

## 复现与证据

```sh
python3 test/modelcheck/wait_protocol_graph.py /tmp/shm-protocol-closure
```

只依赖 Python 标准库。运行器要求三个配置闭合且进展子图无循环，另要求两个反例被找到。保存状态数、源文件指纹和每个反例的完整前后状态轨迹。

证据见 [状态图结果](evidence/ringbuf_protocol_closure_2026-11-21/)。结合 [模型审查](ringbuf_proof_audit_2026-11-21.md) 和 [RC11 检查](ringbuf_rc11_validation_2026-11-21.md)，当前结论是：在明确的通知完成、处理进展和调度前提下，协议抽象有闭合与进展证据；整个 C++ 实现的参数化精化证明、弱内存无限执行证明和外部独立审查仍未完成。
