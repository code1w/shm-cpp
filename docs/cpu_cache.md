# CPU 缓存与伪共享：RingHeader 为什么对齐到 64 字节

本文档面向初次接触本项目的开发者，讲解 CPU 缓存的基础知识，以及这些知识如何决定了 `RingHeader` 的布局（`struct alignas(64) RingHeader`）。涉及的代码位于 `include/shm_ipc/ringbuf.hpp`。

文中的延迟数字均为数量级的典型值，随 CPU 型号和负载变化，仅用于说明量级差异，不是本项目的实测结果。

---

## 1. 为什么需要缓存

CPU 的运算速度远快于内存。访问主内存一次需要上百个时钟周期，而一次加法只要一个周期。为了弥补差距，CPU 在核心和内存之间放了几层容量小但速度快的缓存：

```
  核 0                      核 1
┌────────┐                ┌────────┐
│  L1    │ 32~48KB        │  L1    │      每核私有，~1ns（约 4 周期）
├────────┤                ├────────┤
│  L2    │ 256KB~2MB      │  L2    │      通常每核私有，~3-5ns
└───┬────┘                └───┬────┘
    └───────────┬─────────────┘
          ┌─────┴─────┐
          │    L3     │ 数 MB ~ 数十 MB       多核共享，~10-20ns
          └─────┬─────┘
          ┌─────┴─────┐
          │   主内存   │                       ~60-100ns
          └───────────┘
```

读取数据时先查 L1，没有再查 L2、L3，最后才访问主内存，找到后把数据逐层填回。这种方式依赖**局部性**：刚访问过的数据很可能马上再访问（时间局部性），附近的数据也很可能被访问（空间局部性）。

## 2. 缓存行：缓存管理的最小单位

缓存不是按字节而是按**缓存行（cache line）**管理的。x86-64 上缓存行是 **64 字节**。内存被硬件固定划分为一个个"64 字节对齐的块"，缓存行边界就是这些块的边界（地址的低 6 位是行内偏移，其余位决定是哪一行）：

```
地址 0x1000 = 0b ...0001 0000 0000 0000   低 6 位全 0 → 缓存行起点
地址 0x1040 = 0b ...0001 0000 0100 0000   下一行起点
```

行边界由硬件决定，不需要任何人"保证"。需要保证的是**你的对象放在哪里**：对象的起始地址不一定是 64 的倍数，不对齐的对象可能骑跨两个缓存行，或与别的数据同行（见 6.1、6.2）。

```
地址:  0                64               128
       ├── 缓存行 0 ────┼── 缓存行 1 ────┼── 缓存行 2 ──
```

- 读取任意一个字节，整个 64 字节的缓存行都会被搬进缓存。
- 写入任意一个字节，也是以整行为单位获得写权限。
- 空间局部性正是依赖这一点：顺序读数组时，后面的元素已经随同一行到了缓存里。

这条规则对多线程程序有一个重要后果，见第 4 节。

---

## 3. 缓存一致性：MESI

每个核都有私有缓存，同一个内存地址可能同时出现在多个核的缓存里。硬件用**缓存一致性协议**（x86 上是 MESI 的变体）保证各核看到一致的数据。每个缓存行在每个核里处于四种状态之一：

| 状态           | 含义                             |
| -------------- | -------------------------------- |
| M（Modified）  | 本核独占且已修改，内存里的值过期 |
| E（Exclusive） | 本核独占，未修改，与内存一致     |
| S（Shared）    | 多个核都持有，只读               |
| I（Invalid）   | 无效，必须重新获取               |

关键规则：**一个核要写某个缓存行，必须先拿到独占权，这会使其他所有核里的这一行变成 I（失效）。** 其他核下次访问这一行时，只能从写入方的缓存（或更低层）重新取，这是一次跨核的缓存未命中，延迟通常在几十到上百纳秒。

```
核 0 写缓存行 X:   核 0: M   核 1: I        ← 核 1 的副本被作废
核 1 读缓存行 X:   核 0: S   核 1: S        ← 核 1 从核 0 取数据，核 0 降级为 S
核 1 再写 X:       核 0: I   核 1: M        ← 核 0 的副本被作废
```

当两个核反复读写同一缓存行时，这一行在核之间来回搬运，称为 **cache line ping-pong**。

---

## 4. 伪共享（false sharing）

缓存一致性的粒度是缓存行，而不是变量。如果两个**逻辑上毫无关系**的变量恰好落在同一个缓存行里，它们的读写就会互相干扰：

```
同一缓存行: [ 变量 A (8B) ][ 变量 B (8B) ][ ...... ]

线程 1（核 0）：频繁写 A
线程 2（核 1）：频繁写 B
```

线程 1 写 A 会使核 1 里的这一行失效；线程 2 写 B 又使核 0 里的这一行失效。A 和 B 并不共享数据，却因为同在一行而发生 ping-pong。这就是"伪"共享：共享的只是缓存行，不是数据。

后果是性能下降而不是结果错误，所以不容易发现。典型症状：单线程很快，加上第二个线程后吞吐反而下降，且代码里看不出任何锁或竞争。

## 5. SPSC 环形缓冲区的热点

SPSC 环的生产者和消费者分别在两个核（甚至两个进程）上运行，热路径上每次操作都读写控制变量：

| 变量            | 写者                                      | 读者                     |
| --------------- | ----------------------------------------- | ------------------------ |
| `write_pos`   | 生产者（每次写入后 store）                | 消费者（判断有无数据）   |
| `read_pos`    | 消费者（每次读取后 store）                | 生产者（判断有无空间）   |
| `reader_wait` | 读方置位、写方清零（仅在读方睡眠/唤醒时） | 写方（`ShouldNotify`） |

如果 `write_pos` 与 `read_pos` 在同一个缓存行：

```
同一缓存行: [write_pos][read_pos][......]
生产者核：   每次写入都改 write_pos
消费者核：   每次读取都改 read_pos
```

两者互不相干，却每一次更新都让对方的缓存行失效。SPSC 环本来只有几次原子操作，这种跨核搬运会直接主导吞吐。

## 6. RingHeader 的布局

`RingHeader` 把三个字段各放在独立的缓存行（`ringbuf.hpp`）：

```cpp
struct alignas(64) RingHeader
{
    std::atomic<uint64_t> write_pos;                ///< 写位置
    char pad1[64 - sizeof(std::atomic<uint64_t>)];  ///< 填充至 64 字节
    std::atomic<uint64_t> read_pos;                 ///< 读位置
    char pad2[64 - sizeof(std::atomic<uint64_t>)];  ///< 填充至 64 字节
    std::atomic<uint32_t> reader_wait;              ///< 读方等待标志
    char pad3[64 - sizeof(std::atomic<uint32_t>)];  ///< 填充至 64 字节
};
```

```
偏移    0: write_pos   (生产者写)                    ┐ 缓存行 0
        8: pad1[56]                                 ┘
       64: read_pos    (消费者写)                    ┐ 缓存行 1
       72: pad2[56]                                 ┘
      128: reader_wait (读方置位、写方清零)           ┐ 缓存行 2
      132: pad3[60]                                 ┘
      192: 结构结束，sizeof(RingHeader) == 192
```

效果：

- 生产者主要写缓存行 0，消费者主要写缓存行 1，互不使对方失效。
- `reader_wait` 单独一行：它只在读方睡眠/唤醒时才被修改，若与 `write_pos` 或 `read_pos` 同行，每次睡眠/唤醒都会连带使热点行失效。
- 读写之间仍有**真共享**：生产者要读 `read_pos` 判断空间，消费者要读 `write_pos` 判断数据。这是必要的，但只在对方更新后才产生一次缓存行传输，不是每次访问都发生。

### 6.1 pad 和 alignas 各管什么

两者缺一不可：

| 手段            | 保证                                               |
| --------------- | -------------------------------------------------- |
| `pad` 填充    | 字段之间相隔一整个缓存行                           |
| `alignas(64)` | 结构起始地址是 64 的倍数，字段才会落在行首而不骑跨 |

如果起始地址不是 64 的倍数，比如从偏移 8 开始，则 `write_pos` 在 `[8,16)`，`read_pos` 在 `[72,80)`。它们虽然相隔 64 字节，但 `write_pos` 与前面其他数据同行、`read_pos` 与后面的字段同行，隔离关系被破坏，填充白费。

### 6.2 在共享内存里如何保证对齐

`RingHeader` 位于 mmap 出来的共享内存起始处，不是编译器分配的栈/堆对象，`alignas` 不会自动约束 mmap 返回的地址，需要另外保证：

- 编译期：`static_assert(sizeof(RingHeader) == 192)`（三行）与 `static_assert(alignof(RingHeader) == 64)` 锁定布局。
- `mmap` 返回的地址按页（4096B）对齐，天然是 64 的倍数。
- `kRingDataOffset = 4096`：header 只占 192 字节，数据区起点放在 4096。这既让数据区页对齐（镜像映射要求，见 `ringbuf_byte_stream.md` 第 11 节），也使数据区头部不会与 header 共用缓存行。
- `RingBuf::Init` 在原地构造 `RingHeader` 前有 `assert` 校验 64B 对齐（仅 Debug 生效，Release 下被 `NDEBUG` 去掉；真正的保证来自上一条：header 总是 mmap 区域的起点）。

另外，`static_assert(std::atomic<uint32_t>::is_always_lock_free)` 保证原子操作是无锁的，否则跨进程共享内存里的原子操作可能退化为进程内的锁，失去意义。

## 7. 项目中其他与缓存相关的设计

这些设计的出发点都是"少触碰对方会写的缓存行"：

- **BatchWriter 快照 `read_pos`**：构造时只 load 一次 `read_pos`（一次可能的跨核缓存行传输），写入过程中只在本地追踪 `write_pos`，`Flush` 时一次性 store。N 次写入的跨核缓存行流量从每次一次降到整批一次（见 `ringbuf_byte_stream.md` 第 9 节）。
- **`reader_wait` 按需通知**：写方只在读方声明睡眠时才写 eventfd，避免每条消息都付一次系统调用及相关的缓存/内核开销（见第 10 节）。
- **顺序写读数据区**：生产者顺序写、消费者顺序读，天然利于硬件预取，且镜像映射让跨环尾的访问仍是一段连续的 VA。

## 8. 移植与调整

- **缓存行大小不总是 64B**：部分 ARM 与 Apple 芯片是 128 字节；一些 Intel 处理器会成对预取相邻两行（L2 的 adjacent line prefetch），效果上接近 128 字节的隔离粒度。本项目面向 x86-64 Linux，64B 够用。
- 移植到其他平台时，可以把 `64` 换成 `std::hardware_destructive_interference_size`（C++17，`<new>`，但部分编译器对它有 ABI 警告，且值在编译期固定，跨进程共享内存时两端必须一致），或直接改成常量 128。改动后 `sizeof(RingHeader)` 与相关 `static_assert`、`kRingDataOffset` 的判断也要同步调整。
- 共享内存布局是跨进程契约：两端使用的 `RingHeader` 定义必须一致，不能一端 64、一端 128。

---

## 9. 小结

| 概念            | 要点                                                                           |
| --------------- | ------------------------------------------------------------------------------ |
| 缓存行          | 缓存管理的最小单位，x86-64 为 64 字节                                          |
| MESI            | 写一个缓存行需先使其他核的副本失效                                             |
| ping-pong       | 多核反复写同一缓存行，行在核间来回搬运                                         |
| 伪共享          | 无关变量同行导致的 ping-pong，只拖慢性能，不影响正确性                         |
| `pad`         | 让三个控制字段各占独立缓存行                                                   |
| `alignas(64)` | 起点对齐缓存行，否则字段骑跨、隔离失效                                         |
| 真共享          | 生产者读 `read_pos`、消费者读 `write_pos` 不可避免，靠批处理等手段减少频率 |
